The model plans, code calculates. An LLM turns a plain-English question into one typed, validated operation. Deterministic tools then compute every number, table, citation and conflict from the loaded records and documents. The model never does arithmetic on domain data, and every answer can be traced to source record IDs.

01

System design

Storage & index01
At startup every JSON/JSONL record and Markdown document (manuals, SOPs, MOC memos, recall notice, regulator letter, repair reports) is loaded and indexed as typed evidence with record ID, well, type and path. The test set loads in about 4 s: 600 wells, 7 areas, 149,877 evidence documents. Optional fields (type and team history, late-entered records, data corrections, plugged wells) are respected.
Planner02
Picks 1 of 30 operations: 17 core (status, trends, spills, downtime, heatmap, compliance, containment, RCA, costs, shared knowledge, document Q&A, and 4 writes) plus 13 document-driven tools added for new data (including a conversation-wide triage). It sees only areas, users, well-ID ranges and the asking user's last 5 exchanges.
Validator03
Rejects unknown wells, areas, dates and fields. Explicit values in the question override the model's. Fleet tools take well and area scope only from the question, not from earlier answers. Year-less past dates never resolve into the future. Writes need explicit declarative feedback detected by rules; questions, quotations, hypotheticals and "don't save" never write.
Rules from documents04
Deadlines, thresholds and approvals are parsed from the documents, never hard-coded: OPS-1 gas response (24 h, then 12 h from 1 Jan 2027), OPS-3 status precedence, OPS-5 cold weather, MOC validity and extensions, recall model and lots, the regulator letter's scope, and per-type production thresholds (T200/T350/T500). Each rule is cited.
Memory05
Shared: corrections (original value, author, reason, scope), notes, unconfirmed claims (e.g. "pump was swapped": kept attributed, never overwrites records, flagged when second-hand), and well-type rules. Private: per-user history and display preferences (sort order, $k). Stored in state.json with atomic saves.
Conflicts & honesty06
Shows disagreements instead of picking a side: claim vs record, note vs inspection, and second-hand reports. When the data can't answer, it says so: no pressure data, no production volumes. It offers labelled proxies instead.
Resilience07
A deterministic planner takes over if the model fails, and answers are flagged fallback.

Models and cost

Gemini 3.5 Flash-Lite (planner and synthesis), about 2–5 s per hosted answer, on free-tier keys with app-side rate caps and a 10-minute plan cache. Gemma 4 was tested as a drop-in planner with the same prompt and validator: every plan that returned was correct, but free-tier capacity (429/500/503) and 40–60 s latency ruled it out for the live run.

Verification

Sample: 25/25 acceptance checks over the 18 scenarios, 109/109 independent domain checks, 27 provider checks, and adversarial write-routing probes. Test set: every final answer was checked against an independent oracle computed straight from the raw files.

Next steps

Planner-level multi-step plans (chaining tools generally, beyond triage); entity state over time as a first-class store (installed parts, approvals); a semantic document-rule extractor so new SOP clauses become checkable rules without code; and a UI for confirming or rejecting claims.

✓What worked

  • Document-driven rules carried most of the score. Deadlines, approvals, lots and letter scope were read from the new documents at run time, so the T500 type, MOC extensions and the mid-period SOP revision were handled without special cases.
  • The two-level memory design held up under adversarial multi-user turns. It kept claims unconfirmed and attributed, separated first- from second-hand reports, and kept one user's preferences private.
  • Honest refusals: Q1 and Q2 refuse to invent data the dataset doesn't hold.

!What didn't, and why

  1. Our first live run scored 0/11. Two causes:
    • The planner schema's well bound grew with the fleet (600), and Gemini rejected it, so every turn silently fell back to the rule-based planner.
    • The original 17-operation menu had no way to express MOC approvals, recall lots, note-to-response joins or letter scope.

      Fix: a fixed schema bound, plus 13 general document-driven tools.

  2. Topic references across turns first narrowed fleet questions to wells from earlier answers. Fixed: scope now comes only from the question.
  3. Two gaps closed by generalising.
    • Q7: ranking now weighs an overdue mandated check above a not-yet-due one, and crew dispatch weighs trip logistics.
    • Q9 t6: prioritising across a conversation now has a deterministic triage tool. It collects every well discussed and ranks them safety > compliance > unexplained production loss > equipment.
    • Q7's exact order remains a judgement call. The score is printed in the answer so a reviewer can audit it.
